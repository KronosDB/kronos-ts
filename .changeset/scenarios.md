"@kronos-ts/test": minor
---

Tests run against the app you built. `fixture(app)` replaces `testFixture`, scenarios are written in the shapes an event model is written in, and assertions are plain functions of the outcome.

- A test composes its app the way a process does, `kronos({ … })` over entries carrying their stores and buses, with the log wrapped in `recordingEventStore(…)` and the command bus in `recordingCommandBus(…)` where they are built, and hands the fixture the app: `fixture(app)`. The fixture finds the log and the buses on `app.eventStores`, `app.commandBuses` and `app.queryBuses` (`@kronos-ts/core`). An app whose log or command bus is not recorded does not compile, a processor reading an unrecorded log included; the query bus need not be recorded. The same checks run when the scenario does, naming the wrapper to add. An app with more than one event store, command bus or query bus is refused when the scenario runs: build the fixture's app from the configuration of the module under test.
- `recordingEventStore(store, { clock })` holds the store's deadlines in memory against `clock` (an `advanceableClock()`, the one the app's tasks are built on) and fires them through the store on `advance`. The log stays the real one. Only a fixture whose log was given a clock has `.advance(…)` and accepts `scheduled(…)` and `cancelled(…)`, at compile time. Given events are stamped from that clock.
- `fixture(app).given(...events).when(act).then(...assertions)` runs the scenario and resolves with its `Outcome`. A fixture is one world: `.and` continues it for the next step (`.then(...).and.when(...).then(...)`), which replaces consecutive `run` calls; build a fresh app and fixture per scenario. `fixture()` also takes a promise of the app. Once the scenario is judged the fixture stops the app, so a test app that holds more (a database to drop) releases it in its own `stop`.
- `given` events now reach projections. They are handed to the app's processors as a replay (`ctx.isReplay()` is true) while the recorders hold: a command an event handler dispatches is not sent (`send` resolves to `undefined`) and a deadline it arms is not armed. Before, given events skipped every processor, so a read model could only be tested through events arriving.
- `fixture(app).storyline(query(Q, payload)).shows(expected).after(...events).shows(expected)` walks one read model through its states, each judged once the events before it are handled.
- An assertion is `(outcome) => void | Promise<void>`: it returns when the claim holds and throws when it does not. `Outcome` has `act`, `result`, `threw`, `error`, `events`, `commands` and `app` (the `App`); `TimedOutcome`, the outcome of a fixture whose log has a clock, adds `schedules`. The built-ins are such functions: `events(...)`, `noEvents()`, `commands(...)`, `noCommands()`, `result(value)`, `error(matcher)`, `scheduled(...)` and `cancelled(...)`. `then(event(A), command(C))` becomes `then(events(event(A)), commands(command(C)))`. A function claims a throw by carrying `claimsError: true`, as `error()` does.
- `then` reports every failing claim, not only the first. `.await(...)` is gone.
- `recordingEventStore` and `recordingCommandBus` gain `hold(on)`.
- Removed: `testFixture`, `TestFixture`, `RunOutcome`, the free-standing `given(...)` and `scenario()`, the `Scenario` value, `Judgement`, `FixtureOptions`, `FixtureLists`, `FixtureResources`, `FixtureScope`, `FixtureInfrastructure`, `InfrastructureFactory`, `FixtureEventHandler`, `FixtureUnitOfWork`, `PartialProcessor`, `IfAdvanceable`, `ClockOf` and `controllableSchedulingEventStore` (use `recordingEventStore(store, { clock })`).
